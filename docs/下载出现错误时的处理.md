# 下载错误时的处理

本文总结下载器在"浏览器下载文件出错"时的各种处理机制。相关代码以 `src/ts/download/DownloadControl.ts` 为主，错误由后台脚本 `src/ts/background.ts` 转发。

## 错误从哪里来

本下载器把文件 URL 发给浏览器（`chrome.downloads`）建立下载，浏览器负责实际下载。下载成功或失败时，后台脚本通过 `chrome.downloads.onChanged` 收到结果，再转发给前台页面。前台根据错误码决定如何处理。

浏览器下载可能返回的错误码（`detail.error.current`）：

| 错误码 | 含义 |
| --- | --- |
| `USER_CANCELED` | 用户取消下载（例如关闭"另存为"对话框），或下载被 IDM 等接管 |
| `SERVER_BAD_CONTENT` | 服务器返回 404，文件不存在 |
| `SERVER_FAILED` | 服务器端错误，通常是 500 |
| `NETWORK_FAILED` 等 | 网络失败等其它错误 |

## 处理总览

```
浏览器下载出错（download_err）
        │
        ├─ USER_CANCELED ───────────────► 跳过文件（视为完成，不累计失败）
        │
        ├─ 其它错误码 ──► 是否暂停/停止？
        │                    ├─ 是 ──► 不做处理（等恢复后再说）
        │                    └─ 否 ──► 累计该文件失败次数 +1
        │                                 ├─ 未达到上限（< 3）──► 复位任务状态，重试
        │                                 │       └─ SERVER_FAILED 且有缩略图 ──► 改用缩略图 URL 重试
        │                                 └─ 达到上限（= 3）──► 跳过文件：
        │                                       ① log.error
        │                                       ② 保存错误记录 txt 到本地
        │                                       ③ 视为完成，自动开始下载下一个文件
```

## 各种情况下的具体处理

### 1. 用户取消下载（USER_CANCELED）

用户取消保存、或下载被 IDM 等接管时，下载器也收得到错误信号。

- 直接跳过这个文件，视为"已完成"，继续下载下一个
- **不累计失败次数**（不是下载器/服务器的问题，重试无意义）

### 2. 404（SERVER_BAD_CONTENT）

文件不存在，通常重试无意义，但为了统一处理仍**纳入失败计数**：

- 记录错误日志
- 累计失败次数，未达到上限就重试（一个 404 文件最多会被尝试 3 次）
- 达到上限后跳过，并生成错误记录 txt

### 3. 服务器端错误（SERVER_FAILED，通常是 500）

可能是获取原图时出错，优先尝试换一种方式下载：

- 累计失败次数，未达到上限时重试
- 重试时如果这个文件存在缩略图 URL（`retryUrl`），**交换原图 URL 与缩略图 URL**，改用缩略图下载，避开原图 500；如果缩略图也失败，下次重试会再换回原图 URL
- 如果这个文件**没有缩略图 URL**（附件类文件，如 zip / 音视频，它们没有 `retryUrl`）：沿用旧行为——**第一次失败即跳过**，不入计数循环；跳过时会生成错误记录 txt

### 4. 其它错误（NETWORK_FAILED 等）

- 记录错误日志（"Will try again later"）
- 累计失败次数，未达到上限就重试；达到上限后跳过并生成错误记录 txt

## 失败计数机制（retryCount）

为了避免无限重试，下载器对每个文件累计失败次数，达到上限后跳过。

- **上限**：`Config.retryMax`，当前为 3。累计失败 3 次后不再重试（第 1、2 次失败重试，第 3 次失败后跳过），即一个文件最多实际尝试 3 次
- **计数键是 fileID，不是 URL**：同一个文件在 SERVER_FAILED 重试时会交换 url / retryUrl，两次失败上报的 URL 可能不同；用 fileID 才能保证次数始终累计到同一个文件上，不会被绕过或与别的文件混淆
- **清除时机**：
  - 文件下载成功（收到 `downloaded`）→ 删除该文件的计数
  - 开始**全新一轮**下载（不是"暂停后续传"）→ 清空全部计数，重新给予重试机会
  - 暂停 → 继续下载：**不清空**，同一轮任务继续累计，避免通过暂停反复刷新次数

## 重试时的任务状态复位

重试前先把该任务的状态从"下载中"复位为"未开始"，再以同一个下载槽位重新建立下载。

另外每次发起下载前都会经过用户设置的下载间隔（`DownloadInterval`），失败后的重试同样受这个间隔约束，不会瞬间打爆请求。

## 超过上限后：跳过文件并保存错误记录 txt

达到上限跳过一个文件时，会做三件事：

1. `log.error` 输出一条 `Retry limit reached, this file has been skipped.` 日志
2. 生成一份**错误记录 txt** 保存到本地（见下）
3. 把这个文件视为"已完成"（`downloadSuccess`），从而自动开始下载下一个文件

### 错误记录 txt 的规则

**触发场景**：

- 累计失败达到上限后跳过
- SERVER_FAILED 且文件没有缩略图 URL 可用时跳过（附件类文件）

**不生成记录的情况**：下载器自己生成的文本文件（正文 txt / HTML）。它们的 URL 是 `blob:`，而且本身就是下载器生成的文件，失败后重新下载即可，不需要留档。

**命名**：与原始文件**同一目录、同名**，只把后缀名换成 txt。先用与下载时相同的命名规则生成原始文件的完整文件名，再把末尾扩展名替换为 `.txt`。例如原始文件是 `creator/2026-01-01-标题/0.jpg`，错误记录就是 `creator/2026-01-01-标题/0.txt`。

**内容**（纯文本）：

```
Download failed

URL: <最后一次下载时使用的 url>
Error Code: <错误码，如 SERVER_FAILED>
File: <原始文件的完整文件名（含路径）>
```

**保存方式**：向后台发送 `save_file_no_replay` 消息，由后台直接下载这个 txt。该通道**不返回下载状态**，不会触发下载成功/失败流程，也不会影响失败计数；`conflictAction` 为 `overwrite`，同名文件会被覆盖。

## 暂停/停止与其它边界情况

- **暂停或停止状态下收到失败回包**：不做任何处理（不重试、不跳过），等用户恢复/重新开始后再说
- **找不到该文件的任务记录**：忽略（防御性处理，正常不会发生）
- **文件下载成功**：清除该文件的失败计数

## 补充：不算"错误"但会中断/跳过下载的情况

以下情况不是下载错误，但会导致某个文件不下载或整个下载流程暂停，列在这里便于区分：

- **文件名异常（变成 UUID 等）**：下载受其它扩展影响导致文件名不符预期 → 提示用户并暂停下载
- **今日下载总量达到上限**（如果开启了每日限额）：暂停下载（不是错误，恢复后继续）
- **重复文件检测**：同一个文件之前已经下载过 → 下载前直接跳过（`skipDownload`），视为"已完成"，不进入错误处理流程

## 相关代码位置

| 位置 | 内容 |
| --- | --- |
| `src/ts/Config.ts` | `retryMax`：允许的累计失败次数上限 |
| `src/ts/download/DownloadControl.ts` | `bindEvents` 中 `download_err` 分支（错误码分发）；`downloadError`（计数与重试）；`saveErrorRecord`（生成错误记录 txt）；`createDownload`（重试时切换缩略图 URL）；`startDownload`（新一轮下载清空计数） |
| `src/ts/download/Download.ts` | 发起下载、下载间隔等待、重复文件预检 |
| `src/ts/download/DownloadInterval.ts` | 下载间隔（重试也受其约束） |
| `src/ts/background.ts` | `chrome.downloads.onChanged` 收集错误并转发；`save_file_no_replay` 消息处理（保存错误记录 txt） |

> 注：下载流程里还有一个 `EVT.fire('downloadError')` 事件，目前没有模块监听它，属于预留。
